# 性能基线

本次基线于 2026-10-01 使用合成数据运行，完整结果见本机生成的 `output/performance-baseline.json`。150,000 点路线的取景计算和 500 段范围切换是最明显的后续优化目标；此次只建立测量依据，没有改变取景、轨迹或标签算法。

## 重跑

在已按锁文件安装依赖的项目根目录执行：

```sh
pnpm run build
pnpm run benchmark
```

默认使用本机 Chrome。已安装 Playwright Chromium 的环境可执行 `TRIPREEL_PERF_CHANNEL=chromium pnpm run benchmark`；只测纯 CPU 时执行 `pnpm run benchmark --cpu-only`。后一次运行会覆盖 JSON 报告。请关闭其它密集计算和图形测试，完整运行通常需要约一分钟，较慢机器可能更久。

脚本创建随机本机端口和新的浏览器上下文，明确排除 4173；服务端禁止上游请求，浏览器禁止非本次来源的网络请求。500 段记录使用从 2027-01-01 开始、每天一段的合成日期和中国大陆范围内的合成站点坐标，全部冻结路线，不读取个人浏览器数据。结束时关闭上下文、浏览器和服务。本次上游请求数和外部请求数均为 0。

## 环境与方法

| 项目           | 本次值                                        |
| -------------- | --------------------------------------------- |
| Node.js        | v24.14.0                                      |
| 系统           | Darwin 25.6.0，arm64                          |
| CPU            | Apple M5 Pro，18 个逻辑核心                   |
| 浏览器         | Chrome 154.0.8037.93，无头模式                |
| 图形后端       | ANGLE / Vulkan / SwiftShader 软件渲染         |
| 浏览器视口     | 1280 × 720，设备像素比例 1                    |
| CPU / 页面筛选 | 每项 3 次预热、15 个测量样本                  |
| 页面回放       | 60 帧预热、300 个 rAF 间隔样本，32×，开启跟随 |

CPU 测量直接调用公开的 `filterTrips`、`fitInViewport`、`buildTimeline` 和 `replayFrame`。取景输入为预先转换好的 Mercator 点，采用 48° 倾斜和标题、播放栏遮挡；坐标转换、生成测试数据及浏览器绘图不计入其耗时。每个样本的操作次数记录在 JSON 中，统计值为每次操作的耗时。

页面筛选通过真实输入事件触发，分别统计同步处理耗时，以及输入到两次 `requestAnimationFrame` 回调后的累计耗时（JSON 字段 `throughNextFrameMs`）。后者包含等待下一轮绘制的时间，不代表 GPU 已完成绘制。回放统计的是 rAF 回调间隔，不能当作屏幕实际呈现帧率或视频编码速度；尤其不能把本次软件渲染结果外推为硬件加速表现。

所有 p95 均采用 nearest-rank 方法；15 个样本时 p95 等于最大样本值。这是一台机器上的基线，不是跨设备性能承诺或 CI 硬性阈值。

## 实测结果

下表为中位数 / p95，单位为毫秒。单路线筛选仅筛一条记录，不遍历其几何点，因此不能用来评价大规模行程列表。

| 单路线点数 |              筛选 |              取景 |      回放位置 |
| ---------: | ----------------: | ----------------: | ------------: |
|      1,000 | 0.00021 / 0.00549 |     12.99 / 22.17 | 0.030 / 0.040 |
|     10,000 | 0.00025 / 0.00032 |   127.96 / 141.05 | 0.182 / 0.222 |
|    150,000 | 0.00025 / 0.00029 | 1826.56 / 1894.16 | 3.087 / 3.589 |

500 段场景每段有 100 个点，总计 50,000 个点。保存及首次页面更新合计约 1048.2 毫秒，仅测一次，不列为分位数。

| 500 段场景                         | 中位数 |    p95 |
| ---------------------------------- | -----: | -----: |
| 纯 CPU：筛选全部 500 段            |  0.774 |  1.083 |
| 纯 CPU：按编号筛至 100 段          |  0.197 |  0.246 |
| 纯 CPU：建立回放时间线             |  1.030 |  1.132 |
| 纯 CPU：取最后一段的回放位置       | 0.0070 | 0.0081 |
| 页面：筛至 100 段，同步处理        |  104.3 |  137.4 |
| 页面：筛至 100 段，含两次 rAF 等待 |  166.2 |  199.1 |

| 页面：恢复 500 段，含两次 rAF 等待 |  550.0 |  567.7 |

500 段范围内的实际页面回放测得 rAF 间隔中位数 33.3 毫秒、p95 33.4 毫秒，300 个样本中有 3 个超过 50 毫秒，平均回调频率约 29.70 Hz。约 10.10 秒的采样窗口内，`#map-place-labels` 出现 547 次子节点替换，共添加 1175 个节点、移除 1174 个节点，约每个采样帧替换 1.82 次。计数来自外部 `MutationObserver`，没有修改生产代码或替换其计时函数。

## 后续优化顺序

1. 优先处理取景计算。现有取景对全部点和多个可见矩形反复求解；150,000 点约 1.83 秒的 CPU 中位数会阻塞同步交互。后续可评估按几何版本缓存输入、复用取景约束或减少求解点；任何减少点数的方案都必须再用完整铁路曲线及飞机高度检查最终视口，防止裁掉绕行或弧线。
2. 分解页面范围切换的耗时。500 段纯筛选约 0.77 毫秒，而页面同步处理约 498 毫秒，说明列表重建、重复校验、路线层更新和自动取景的组合需要进一步分段测量。优先验证重复取景和绘图工作的收益，再决定列表是否需要分批渲染。
3. 减少标签重建。内容未变时复用标签及 SVG 节点，单独更新位置；用同一计数器比较替换次数，同时保留播放、同城合并、缩放、全屏及遮挡回归。当前计数说明存在频繁节点替换，尚未独立测出其耗时占比。
4. 最后评估长路线回放。150,000 点单次位置计算约 3.09 毫秒，可考虑按路线版本预计算累计距离并二分定位；须验证端点、折返、连续路线、旧版 `legs` 及地图/视频一致性。当前基线不足以证明这是页面回放的主要瓶颈。
